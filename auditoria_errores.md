# Auditoría de errores — Tienda online "Cronos Elegance"

**Repositorio:** naranciakang/proyectofinal
**Ruta del sitio:** `ProyectoFinal/proyectofinal/`
**Fecha:** 2026-09-21
**Alcance:** revisión estática de código + ejecución local del sitio (Django dev server sobre SQLite temporal, réplica del repo en entorno aislado) + navegación automatizada (Playwright) en escritorio (1366×768) y móvil (390×844) + linters/checks nativos de Django + auditoría de dependencias (`pip-audit`).

## 0. Stack identificado

- **Backend:** Django 5.2.6 (Python), app única `principal`.
- **Base de datos configurada:** MySQL (`proyecto`, `root`/`root`, `localhost:3306`) vía `mysqlclient`. Existe además un `db.sqlite3` vacío y sin uso commiteado en el repo.
- **Frontend:** plantillas Django + CSS propio + Bootstrap 5.3.3 (CDN jsdelivr) + Font Awesome 6.4.0 (CDN cdnjs) + iconos hotlinked desde `img.icons8.com` + imágenes de stock desde `images.unsplash.com`. JS vanilla (sin framework, sin bundler, sin `package.json`).
- **Pasarela de pago:** Transbank Webpay Plus (`transbank-sdk` 6.1.0), ambiente `INTEGRATION` (pruebas), configurado en `settings.py` y duplicado (con otra API key) en un archivo muerto `transbank_config.py`.
- **Analítica:** ninguna (no se encontró Google Analytics, GTM, Meta Pixel ni similar en ninguna plantilla).
- **Email:** SMTP Gmail con contraseña de aplicación hardcodeada en `settings.py`.
- **Despliegue:** `gunicorn` + `whitenoise` (Procfile), sin CI, sin README, sin `.env`, sin `.gitignore`.

## 2. Metodología de verificación en local

No fue posible levantar el proyecto tal cual está configurado (requiere MySQL local con credenciales `root`/`root`, inexistente en el entorno de pruebas). Para verificar el comportamiento real se instalaron las dependencias de `requirements.txt` (excepto `mysqlclient`, sin librerías nativas de MySQL disponibles) sobre una **copia aislada** del repositorio (no se modificó el repositorio original) y se apuntó `DATABASES` a SQLite únicamente en esa copia, manteniendo el resto de la configuración (`DEBUG=False`, mismas vistas, mismos templates) para reproducir el comportamiento real. Sobre esa copia se ejecutaron migraciones, se cargaron 3 productos y 1 usuario de prueba, se levantó `runserver` y se navegó con Playwright (Chromium) y `requests` por home, listados, buscador (filtros de `/productos/`), ficha de producto, carrito, checkout (hasta antes de confirmar el pago con Transbank), cuenta de usuario (registro/login/recuperación), páginas estáticas y error 404, en escritorio y en 390×844.

### Los 5 hallazgos más críticos

1. **C1 — IDOR en carrito de compras**: cualquier persona, sin autenticarse, puede eliminar o alterar la cantidad de artículos del carrito de otro usuario simplemente adivinando un `item_id` numérico (`/eliminar-item/`, `/actualizar-cantidad/`), confirmado con una prueba reproducible entre dos sesiones.
2. **C2 — Creación de productos sin autenticación**: la ruta pública `/inventario/` permite a cualquier visitante publicar productos (con imagen) directamente en la tienda, sin ningún control de acceso; confirmado creando y viendo el producto en la home real.
3. **C3 — Secretos reales expuestos en el repositorio**: contraseña de aplicación de Gmail, `SECRET_KEY` de Django y credenciales de base de datos versionadas en texto plano en `settings.py`.
4. **C4 — Fotos de producto rotas en toda la tienda**: con la configuración tal cual está commiteada (`DEBUG=False`), ninguna imagen subida a `/media/` se sirve, dejando sin foto todo producto en home, listados, ficha, carrito, checkout y boleta.
5. **C5/C8 — Checkout roto por función duplicada**: dos definiciones de `checkout()` en el mismo archivo hacen que la versión realmente activa permita comprar sin iniciar sesión pero falle con error 500 al intentarlo, por incompatibilidad con el modelo `OrdenCompra`.
